# ADR 0022 — M4c-7d Native Rendering and PSD Metadata Classification

**Decision:** accept the bounded *research finding*, **do not approve PSD writes**

**Date:** 2026-10-13

**Research basis:** `develop@80af5544293a289264759cfa89ea39d28f43cf51`

**Frozen v0.1 main:** `5526dc4465c4e79ad7f2757d06b3b1693642b8af`

## What has been verified

Two separately executed Adobe Photoshop 2026 saveAs experiments used the
same frozen, exact-hash PSD with a single group rename (`Group 1` to
`Group 2`). Each experiment retained an unchanged-original save control.
All inputs and outputs were disposable research files under ignored
`target/`; no public YuTool PSD mutation is enabled.

Independent `psd-tools 1.20.0` previews of the *original* PSD disagreed
with native Photoshop PNG renders at **160/20,000 RGBA pixels**. Those
same previews from each *Photoshop-saved* PSD agreed completely with
the corresponding native Photoshop PNG. Importantly, native Photoshop
PNG vs native Photoshop PNG before/after saving showed **zero changed
pixels**, for both original control and edited input, on both runs.

The 160 pixels are bounded by `[26,25,65,97)`; all changes are in R/G/B,
none in alpha, and maximum channel delta is 11. The repeated pattern is
identical. This establishes that the earlier independent-parser
source-vs-save preview difference **was not evidence of native Photoshop
rendering damage in this one fixture**. Do not generalize to masks,
effects, ICC/color conversion, text, arbitrary PSD/PSB or other editors.

## Raw metadata investigation

Adobe's PSD File Format Specification and psd-tools constants identify
the resources:

| ID | Type | Observed change | Decision |
|---:|---|---|---|
| 1050 | Slices | 20-unit `nested-group-control` vs 12-unit `nested-group` document-name fields | 16-byte file size difference **explained for this fixture**; each resource's prefix and tail bytes match exactly |
| 1058 | EXIF data 1 | Equal within one saved pair, differing by a few bytes in another or between separate saves | **Not fully decoded**, may not be ignored |
| 1060 | XMP metadata | `DocumentID`, `InstanceID`, `History`, sometimes `ModifyDate`/`MetadataDate` differ | Document identity/history semantic changes; no blanket exclusion |
| `shmd` | Layer metadata settings | Four `cust` payloads, each 52 bytes, differ across saved files | **Opaque/undocumented semantic content**, blocked |

The observed XMP changes, EXIF changes and `shmd` payload variation
also occur between repeated native Photoshop saves of unchanged inputs,
so some changes are clearly generated by the editor. That **does not
prove** they have no effect on editing behavior, identifiers, history,
linkages or provenance. Unknown metadata must not be silently discarded
or normalized to make a gate turn green.

The Slices `1050` change was specifically inspected at the PSD byte
level: 4-byte version 6, 16-byte rectangle, 4-byte Unicode-name count,
then name bytes, with an identical suffix. This explanation is scoped
only to the exact serialized fixture and must not authorize general
Slice resource rewriting or a production metadata whitelist.

## Gate outcome and what remains

- M4c-7d *independent vs Photoshop native pixel investigation*: **PASS**
  for exactly one simple group fixture (two runs).
- M4c-7d Slices file-name length-difference explanation: **PASS**
  for this one serialized specimen.
- General EXIF/XMP/`shmd` preservation and metadata semantics: **BLOCKED**.
- M4c-7e production authorization: **BLOCKED**; `main` unaffected.

Next scope expansion must remain **research only**: new ordinary pixel
layers, UTF-16/legacy name compatibility and duplicates must be tested
against new exact-hash fixtures before being added to any admission
contract. Special Background, non-RGB/high-bit and effects/Smart Object
mutation stay denied. Do not implement or expose `yu psd rename`
or general save based on this one successful group fixture.
