# ADR 0026 — M4c-10 Multilingual Dual-Name and Photoshop Layer ID Stability

**Date:** 2026-10-13

**Status:** Controlled research PASS; production PSD mutation remains **BLOCKED**

**Base:** `develop@6002b1b2b844dc48ceb11357cbc814d2a041366e`

**v0.1 frozen `main`:** `5526dc4465c4e79ad7f2757d06b3b1693642b8af`

## Decision

Accept the M4c-10 experiment as evidence that **in two particular
Photoshop 2026 native-generated PSDs**, a strictly SHA-bound,
equal-length Unicode `luni` plus legacy Pascal/GB18030 synchronized
name patch survives native save/close/reopen and keeps the target
Photoshop layer ID intact. Also accept two scratch-only experiments
showing `lyid` identity can survive **layer reorder** and
**moving into a newly created group** in one duplicate-name fixture.

Neither result establishes a generic Photoshop writer, a universal
legacy text encoding, a guaranteed ID across arbitrary PSD edits, or
full preservation of opaque metadata. The release decision stays
`PSD_PRODUCTION_MUTATION_BLOCKED`.

## A. Synchronized non-ASCII names

Sources: *exact SHA-256-bound Photoshop-native* Chinese and Cyrillic
PSD copies from M4c-8. They have ordinary pixel layers with target
`lyid=6` and a second layer `lyid=2`.
No user-selected file or generic input path is allowed. Disposable
outputs are under ignored `target/m4c10-multilingual-sync/run-*`.

| Scenario | Unicode name before / after | Pascal raw hex before / after | Result |
|---|---|---|---|
| Chinese | `测试图层` → `实验图层` | `b2e2cad4cdbcb2e3` → `cab5d1e9cdbcb2e3` | Native Photoshop save/reopen passed |
| Cyrillic | `Слой` → `Тест` | `a7b3a7dda7e0a7db` → `a7b4a7d6a7e3a7e4` | Native Photoshop save/reopen passed |

Both names occupy **eight UTF-16BE bytes** and **eight GB18030
legacy bytes** before and after; no section length, composite,
channel payload, Image Resources, or non-name PSD byte changed in
the *pre-save byte-patched inputs*. The implementation rejects
any other source SHA, raw layer shape, mismatched `lyid`, charset
bytes or name length. Photoshop reopens both synchronized names
correctly. The unmodified save control and renamed saved candidate
have identical independent `psd-tools` decoded pixels in both cases.

**Crucial limit:** GB18030 decoding and byte sequences are observed
for these Photoshop 2026 fixtures/local environment only. Photoshop
files generated by other platforms/versions or with other Pascal
codepages cannot be assumed compatible. A production writer must
discover or explicitly bind the charset and reject ambiguous inputs.

Machine evidence:
[multilingual paired native receipt](../data/m4c10-multilingual-sync-v1.json).

## B. Native layer identity under structural edits

Using the SHA-bound M4c-8 Photoshop-generated PSD with two same-name
`Layer 0` pixel layers (`lyid=6`, `lyid=2`), an independent
research probe performed two *different* Photoshop-native edits on
distinct disposable source copies:

1. **Reorder** the target above the other layer. After native
   save/reopen, `lyid=6` and `lyid=2` are preserved, but their
   *raw PSD record indices are different*.
2. **Group move:** create `M4c10 Research Group` and move the
   target `lyid=6` into it. After native save/reopen, both old
   IDs are preserved, the group receives a new ID, and Photoshop may
   introduce a section-divider record with its own ID.

**Conclusion:** raw record index or text name is not a stable target
identity. When making any rename proposal, bind the exact source
SHA-256, expected globally unique *within-document* `lyid`,
its raw record and logical tree identity *for that source version*.
Reorder/group transformations require a fresh parse and target
revalidation; never reuse a stale raw index or claim cross-document
ID permanence.

[Native structural receipt](../data/m4c10-lyid-reorder-group-v1.json).

## C. Resource, composite and metadata gates

M4c-10 compares the two paired saved control/candidate PSDs without
writing them again. Both multilingual pairs retain the same raw
channel fingerprints and compressed merged image bytes.
**Both pairs still contain resource and/or tagged metadata deltas.**

The M4c-7d/M4c-9 audits already detected:

- XMP Resource `1060` document IDs, instance IDs, history and
  timestamps. These contain provenance and identity semantics.
- EXIF Resource `1058`, a TIFF-structured payload for which general
  preservation remains unverified.
- The Photoshop `shmd/cust` descriptor shape with `layerTime`
  double values in the audited samples. This does not prove that
  every `cust` item can be ignored or safely regenerated.
- Resource `1050` can include a saved document's Slices name, but
  recognizing one name-derived length delta does not permit
  rewriting or ignoring arbitrary Slices resources.

This stage **does not** grant a metadata ignore-list, Photoshop
semantic equivalence certificate, or release permission. See the
[M4c-10 saved pair audit](../data/m4c10-metadata-paired-v1.json).

**M4c-10 is a finished research increment, not a PSD write feature.**
M4c-11 should focus on metadata equivalence and a separately
controlled output-only publication policy proposal; the v0.1
`main` release candidate stays unchanged.
