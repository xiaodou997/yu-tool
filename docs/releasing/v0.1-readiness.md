## Offline installation

Download or transfer a trusted manifest and its matching **inner engine archive**. An Actions artifact is an outer transport ZIP: unpack it first. Check provenance/checksums through a trusted channel; a checksum supplied together with an untrusted archive is not authentication.

```bash
yu engine install --manifest manifest-macos-aarch64.json \
  --archive yu-engine-ag-psd-31.0.2-node22.23.3.yu2-macos-aarch64.zip --json
yu engine activate ag-psd 31.0.2+node22.23.3.yu2 --json
yu psd layer export design.psd --id L0002 -o layer.png --json
```

`--archive` is explicit and never a download fallback. Existing Manifest v1 validation still applies, including its HTTPS URL field, platform and SHA-256. The URL remains package identity but is not fetched on this path. The copied stream is limited to 512 MiB; non-regular/symlink inputs, checksum mismatches, unsafe archives and existing installed versions are refused. Installation does not activate or execute the engine. The source archive is not changed.

## Windows lifecycle evidence

PR #24 observed OS 5 during read-only package removal despite the bounded retry. The log did not identify an owner. This preparation does **not** claim a root-cause repair or silently extend the two-second budget.

Successful removal adds `result.quarantine.attempts` and `elapsed_ms`. Failed quarantine includes attempt/elapsed count, raw OS error, source/destination, source attribute observations and whether the caller's current directory is inside the source. These are diagnostics, not proof of the lock owner or permission cause. Persistent failure preserves the original version and stable `EXECUTION_FAILED` behavior. No elevation, file-unlock utility or copy/delete fallback is used.

The repeated test executes install → explicit activate → inspect → engine info → deactivate → capabilities → remove, ten times using the same isolated data root. Every cycle requires complete cleanup; any failed cycle fails the test. The existing read-only and independent pixel-fingerprint tests remain enabled and run concurrently under Rust's default test execution. Both normal and extracted release executables are checked. A green finite sample is not a guarantee under every scanner/permission configuration; the Windows release gate remains unaccepted until an explicit reliability decision.

## Developer candidate build

Prerequisites: Git, the pinned Rust toolchain, Python 3.11+ and target build prerequisites. Node/Python are not runtime dependencies of the packaged core CLI. Start with a clean, committed checkout; generated results go beneath ignored `target/`.

```bash
python3 -B tools/build_cli_candidate.py \
  --target aarch64-apple-darwin \
  --output-dir target/cli-candidate/macos-aarch64
```

Also supported: `x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`, built on matching runners. Cross-target execution is not supplied. Every invocation performs a locked release build, checks source stability, packages only the CLI, build metadata and a release-status notice, then validates/extracts the ZIP and runs the extracted executable with empty PATH and isolated `YU_DATA_HOME`.

Outputs: source-qualified `yu-0.1.0-dev.<commit>-<target>.zip`, `SHA256SUMS`, `candidate.json`, and a `smoke/bin/yu[.exe]` used for further actual-CLI tests. Metadata records the source commit/tree, compiler, binary SHA-256 and lockfile hashes. Existing output directories are not overwritten. Container determinism is tested for identical binary/metadata inputs; compiler/linker/OS bit-for-bit reproducibility is **not** proven. Toolchain/lock pinning does not establish minimum supported OS versions or signature acceptance.

The workflow uses read-only repository permissions and uploads candidates only after the release executable passes PSD/lifecycle tests. It has no tag, GitHub Release, production upload or signing step. The 30-day candidate artifact retention is temporary validation storage, not durable distribution. A failed build may leave an incomplete local output directory; it is not an accepted candidate.

| --- | --- |

| Project license | Owner decision; no license is selected by this PR |

| Platform signing and supported OS | Explicit signing/notarization policy plus minimum-OS and clean-machine acceptance |
| Durable distribution | Trusted HTTPS release manifests and persistent artifacts; prototype URLs are not production endpoints |
| Release authorization | Explicit approved version/tag and publishing decision |

Every candidate deliberately reports `public_release_ready: false`. The builder cannot turn these gates green or publish. Do not rename a developer archive into a signed/public release without a separate validated release process.
